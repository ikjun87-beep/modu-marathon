# TIERS — 가시성 3층 설계 (나만 / 크루 / 전체 공개)

> 2026-08-01 세션12 · **오너(JJUN님) 방향 확정.** 골프존·GDR 모델 제안 → 조정 3건 수용.
> 이 문서가 크루 격리의 **현행 설계**다. [`BRIEF.md`](BRIEF.md)는 2층(크루만) 전제의
> 적대회의 기록으로, 기각 사유와 측정치는 여전히 유효하나 **결론은 이 문서가 대체**한다.

---

## 1. 한 줄 결론

**가시성을 세 층으로 나누고, 층을 곧 경로로 삼는다.** 그 결과 3라운드를 소모한 A안/B안
논쟁이 소멸하고(층이 경로면 B안이 구조적으로 결정된다), **L3 3건 중 2건이 함께 사라진다.**

---

## 2. 왜 2층이 아니라 3층인가

지금까지의 전제는 "크루로 가른다" 하나였고, 거기서 **웹이 갈 곳을 잃었다**(`BRIEF.md` 4-2).
B안에서 웹 방문자에겐 crewId가 없으므로 랜딩의 사회적 증거를 포기하거나 가짜 크루를 영구히
운영해야 했다 — 이것이 L3 ②의 정체였다.

**3층은 이 문제를 없앤다.** 웹은 "공개하기로 한 사람들"의 층을 그대로 보면 된다. 가짜도
아니고 포기도 아니다. 동시에 "앱을 깐 전원이 한 크루"라는 출시 블로커도 그대로 닫힌다.

그리고 이 구조는 **"혼자 쓰는 앱이 우선"**이라는 오너 원칙을 스키마로 표현한다. 크루에
들어가지 않아도 앱이 완전히 동작하고, 크루는 그 위에 얹히는 층이 된다.

### GDR 매핑

| GDR | 5키로 | 층 |
|---|---|---|
| 내 연습 기록 | 내 러닝 | 1 — 나만 |
| **우리 매장 순위** | **크루 랭킹** | 2 — 크루 |
| **전국 매장 순위** | **전체 공개 랭킹** | 3 — 공개 |

⚠️ GDR의 "우리 매장"은 임의 친구 그래프가 아니라 **소속 그룹**이다. 그래서 크루와 정확히
같은 물건이고, 규칙이 멤버십을 `get()` **1회**로 검증할 수 있다. 이 점이 아래 3-3의 근거다.

## 3. 층의 정의

| 층 | 경로 | 읽기 | 기본값 | 비고 |
|---|---|---|---|---|
| **1 · 나만** | `users/{uid}/{col}/{id}` | 본인만 | **저장 원본** | 크루 없이도 앱이 완전히 돈다 |
| **2 · 크루** | `crews/{crewId}/{col}/{id}` | 크루 멤버만 | **공개** | 초대 코드로 스스로 들어온 곳이다 |
| **3 · 전체** | `{col}/{id}` (**현행 루트 재활용**) | 전원 + **웹** | **비공개(opt-in)** | 랜딩의 사회적 증거 |

`{col}` = `runs`·`guestbook`·`gallery`·`attendance`·`events`·`comments`·`claps`·`profiles`.

## 4. 설계 결정 3건

### 4-1. 루트 컬렉션을 **3층으로 재활용**한다 (새로 파지 않는다)

- **마이그레이션이 0이다.** 기존 13건이 이미 루트에 있다. 새 컬렉션을 파면 그 13건을 옮겨야 한다.
- **웹 코드가 거의 안 바뀐다.** `web/index.html`의 전체 구독이 그대로 3층 구독이 된다.
- **규칙 diff가 작다.** 루트는 `read: if true`를 유지하고 **create에 공개 동의 필드 검증만** 더한다.

⚠️ 단 **기존 13건은 공개 동의를 받은 적이 없다.** 컷오버 때 비우고 손으로 다시 넣는다
(13건이라 이 선택이 싸다 — 이것이 `BRIEF.md` 근거 1의 측정이 지금도 살아 있는 이유다).

### 4-2. 원본은 1층에 두고, 2·3층은 **사본**이다 (이동이 아니다)

| | 사본 방식 (채택) | 이동 방식 (기각) |
|---|---|---|
| 공개 취소 | **사본 delete** — 원본은 안 건드린다 | 상위 층 delete + 하위 층 create |
| 중간 실패 | 사본만 남거나 사라진다. **기록은 안전** | **delete만 성공하면 기록이 순삭된다** |
| 저장 | 러닝 문서는 수백 바이트 — 2~3벌도 무의미한 크기 | 1벌 |
| 동기화 | 수정 시 사본 재푸시 필요 | 불필요 |

**기각 사유가 결정적이다.** 이동 방식의 실패 모드는 `BRIEF.md` R2(`run.ts:141~`의
delete→재생성 우회에서 문서가 순삭되는 사고)와 **정확히 같은 모양**이다. 이미 한 번 진단한
함정을 스키마 차원에서 다시 파지 않는다.

동기화 부담은 작다 — 러닝 기록은 사실상 불변이고, 실제로 바뀌는 경우(워치 거리 정정·종목
수정)는 원본을 고친 뒤 **멱등 `put`으로 사본을 다시 밀면** 된다(`crew.ts`에 이미 있다).

⚠️ **예외: 갤러리 사진.** base64라 문서가 수백 KB다. 사진은 사본을 만들지 않고 **한 층에만**
둔다(올릴 때 대상 층을 고른다).

### 4-3. "친구"는 임의 그래프가 아니라 **크루(그룹)**다

임의 친구 그래프를 Firestore 규칙으로 지키는 것은 **무료 플랜에서 불가능하다.** 근거:

- **규칙은 필터가 아니다.** 쿼리 결과를 걸러주지 않고 "이 쿼리를 허용할지"만 본다. "친구 것만
  보여줘"라는 요청을 규칙이 대신 좁혀줄 수 없다.
- 클라이언트가 `where(uid,'in',[친구들])`을 보내는 방식은 **`in`이 30개 상한**이고, 무엇보다
  **클라이언트가 목록을 조작하면 아무나 읽힌다.** 규칙이 그걸 검증하려면 친구 수만큼 `get()`이
  필요한데 **규칙당 10회 상한**이다(A안이 무너진 것과 같은 함정 — `CREW-GATE.md` §3).
- 팬아웃(내 기록을 친구 수만큼 복사)은 **Spark 쓰기 2만/일**을 금방 먹는다.
- Cloud Functions는 **Spark에서 못 쓴다**(`BRIEF.md` 3절이 커스텀 클레임을 기각한 바로 그 이유).

**그룹은 된다.** 멤버십이 `crews/{crewId}/members/{uid}` 문서 하나라 `get()` 1회로 끝난다.

**연락처 접근은 쓰지 않는다.** 목적은 "친구를 찾는 것"인데 수단의 값이 너무 비싸다 —
`READ_CONTACTS`는 플레이 **민감 권한**(Prominent Disclosure 의무), 매칭하려면 **전화번호를
수집**해야 해서 처리방침을 다시 써야 하고(거짓 고지 3건을 방금 정정한 참이다), 데이터 안전
양식에 항목이 추가된다. **초대 코드가 이미 설계·검증돼 있다**(`CREW-GATE.md` §1) — 카톡으로
코드 하나 보내는 편이 "연락처 권한 허용"보다 마찰이 **낮다**. 러닝 크루엔 이미 단톡방이 있다.

## 5. 규칙 초안

```javascript
// ── 1층 · 나만 ────────────────────────────────────────────────
// 경로에 uid가 있어 소유 검증이 문자열 비교 한 번이다. get() 호출 0회.
match /users/{uid}/{col}/{id} {
  allow read, write: if request.auth != null && request.auth.uid == uid;
}

// ── 2층 · 크루 ────────────────────────────────────────────────
function isMember(crewId) {
  return request.auth != null
      && exists(/databases/$(database)/documents/crews/$(crewId)/members/$(request.auth.uid));
}
match /crews/{crewId} {
  allow get: if isMember(crewId);
  allow list: if false;                    // 크루 열거 금지 — 초대 코드와 같은 원리
  allow create: /* CREW-GATE.md §3 상한 규칙 */;

  match /members/{uid} {
    allow read: if isMember(crewId);
    allow create: if request.auth.uid == uid;   // 초대 코드 검증은 앱이 선행
    allow delete: if request.auth.uid == uid;   // 탈퇴
  }
  match /{col}/{id} {
    allow read: if isMember(crewId);
    allow write: if isMember(crewId) && /* 기존 타입·크기 검증 그대로 */;
  }
}

// ── 3층 · 전체 공개 (루트 재활용) ─────────────────────────────
// read는 현행 유지(웹이 신원 없이 읽는다). create에 **공개 동의**를 강제한다.
match /runs/{id} {
  allow read: if true;
  allow create: if request.auth != null
                && request.resource.data.visibility == 'public'
                && request.resource.data.ownerUid == request.auth.uid
                && /* 기존 타입·범위 검증 그대로 */;
  allow update: if /* 기존 불변 검증(distanceKm·durationSec·kind) 그대로 */;
  allow delete: if request.auth != null
                && resource.data.ownerUid == request.auth.uid;   // ← 전면 개방을 닫는다
}
```

**얻는 것 하나 더**: 3층에 `ownerUid`가 생기면 지금 전면 개방인 `delete: if true`를
**소유 기반으로 닫을 수 있다.** 현행 규칙 주석이 "Auth 도입 시 uid 소유검증으로 교체"라고
예고해 둔 항목이 여기서 회수된다.

⚠️ `get()`/`exists()`는 **경로당 1회**만 쓴다. 10회 상한에 여유를 남긴다.

## 6. L3 3건이 어떻게 처리되나

| L3 | 기존 | 3층에서 |
|---|---|---|
| ① A안/B안/보류 | 미결 | **B안으로 자동 확정.** 층이 경로면 A안(필드)은 한 컬렉션에 3층이 섞여 규칙이 층 판정을 필드로 해야 하고 **색인 7개가 부활**한다 |
| ② 웹 사회적 증거 | 포기 여부 미결 | **소멸.** 3층이 살린다 — 웹은 공개 층을 그대로 본다 |
| ③ `profiles` id 이름→uid | 미결 | **uid로 자동 확정.** 1층 경로가 이미 `users/{uid}/…`다. 동명이인이 서로 얼굴을 덮어쓰던 문제가 **경로에서 사라진다**(`BRIEF.md` 4-3) |

**→ 남는 오너 결정은 App Check 콘솔 등록(물리작업) 하나다.**

## 7. 공개 기본값 정책

| 층 | 기본값 | 근거 |
|---|---|---|
| 1 나만 | — | 저장 원본 |
| 2 크루 | **공개** | 초대 코드로 스스로 들어온 곳이고, "같이 뛰는 사람들"이 크루의 정의다 |
| 3 전체 | **비공개**, 켤 때 한 번 묻는다 | 아래 4가지 |

**자동 공개를 하지 않는 이유 — GPS는 비거리와 다르다**

1. **경로는 집 주소를 드러낸다.** 대부분의 러닝이 집에서 출발해 집으로 돌아오므로 시작점과
   끝점이 겹치는 지점이 곧 거주지다. Strava가 프라이버시 존을 기능으로 파는 이유다.
   → 우리는 경로를 **서버에 저장하지 않으므로**(`run-path.ts` 온디바이스) 지금은 안전하다.
   **공유 카드에 경로를 실을 때만** 이 판단이 필요하다.
2. **심박은 민감정보다.** 세션11에서 "심박이 고지 없이 공개되고 있었다"를 정정한 항목이다.
3. **초기 이탈 요인.** 처음 뛰는 사람의 느린 페이스가 자동으로 전국 목록에 올라가면 그 사람은
   기록을 남기지 않게 된다. 확산에 역효과다.
4. **플레이 데이터 안전** 양식의 "다른 사용자에게 표시됨" 칸이 켜지고, 기본 공개는 심사
   리스크를 키운다.

## 8. 랭킹 축 (GDR의 비거리순·연습시간순)

정렬축을 늘리는 것은 쉽다 — 거리순·페이스순·횟수순 × 주간/월간. 단일 필드 정렬이라 색인도
자동 생성된다.

⚠️ **성별 분리는 권하지 않는다.** 새 개인정보 수집이다. 마스코트가 `m-`/`f-`로 나뉘어 있지만
그건 **캐릭터 선택**이지 성별 신고가 아니며, 이걸 랭킹에 쓰면 선택이 개인정보로 승격돼
처리방침 대상이 된다. 러닝에서는 **연령대·거리 구간(5K/10K/하프)** 분리가 문화에 더 맞고
개인정보 부담이 낮다.

## 9. 살아남은 문제 (봉합하지 않는다)

| # | 항목 | 상태 |
|---|---|---|
| R1 | **과도기 유령 저장** | 유지. 구버전 앱이 루트에 쓴 글이 신버전 사용자에게 안 보인다 → **컷오버 시 루트 write를 즉시 막아** 실패를 눈에 보이게 만든다 |
| R2 | **`run.ts:141~` 우회 경로** | 유지. **컷오버와 같이** 막는다 — 지금 막으면 워치 재동기화가 조용히 실패한다 |
| 4-5 | **운영 관측이 쪼개진다** | **악화.** 층이 셋이라 콘솔 육안 확인이 더 흩어진다. 지금까지 데이터 확인은 전부 콘솔 육안이었다 |
| — | **사본 동기화** | 신규. 러닝은 사실상 불변이라 부담이 작지만, 수정 경로가 늘면 재검토 |
| — | **App Check** | 오너 물리작업. **미적용 모드 1주 관찰 후** 넘긴다(바로 켜면 정상 사용자가 앱을 못 쓴다) |

## 10. 컷오버 순서

1. `tests/`에 **3층 규칙 테스트를 먼저 쓴다** — 통과하는 rules가 없는 상태에서 시작한다(레드).
   기존 `describe('격리 전 기준선 …')` 13건은 **여기서 실패해야 정상**이다.
2. 1층 `users/{uid}/*` 신설 + 앱의 저장 경로를 1층으로. **이 시점까지 앱은 정상 동작**한다.
3. 2층 `crews/*` + 초대 코드(`CREW-GATE.md`) + 크루 상한.
4. 3층 = 루트에 `ownerUid`·`visibility` 강제. **루트 13건을 비운다.**
5. `run.ts:141~` 우회 차단(R2) + 루트 write 차단(R1)을 **같은 배포에서**.
6. 웹을 3층 구독으로 정렬(필터만 추가) + 웹의 하드코딩 `EVENTS` 이관.
7. App Check 미적용 모드 → 1주 관찰 → 적용.

**⚠️ 비공개 테스트(12명×14일)는 7번까지 끝난 뒤에 시작한다.**

## 11. PHASE 2 실제 구현 범위 (세션19~21, 2026-08-16~17)

> 위 §1~10은 **완전한 3층**(1층 나만·2층 크루·3층 전체공개 opt-in)의 원안이다. PHASE 2에서
> 실제로 구현한 범위는 이 원안의 **부분집합**이고, 그 이유를 여기 남긴다 — 다음 세션이
> "왜 8개 컬렉션이 전부 안 옮겨졌지"를 다시 조사하지 않도록.

### 11-1. 1층(나만)은 짓지 않았다
크루 기본값이 항상 "공개"(§7)라, 1층 원본 없이도 **2층(크루)이 곧 저장 원본** 역할을 한다.
"혼자 쓰는 앱이 우선"이라는 원칙(§2)은 크루에 안 들어간 사용자가 기존처럼 동작하는 것으로
충족되고, 진짜 나만 보이는 비공개 저장소가 필요해지면 그때 1층을 짓는다.

### 11-2. 3층(root)은 "옵트인 공개 사본"이 아니라 "웹이 실제로 보는 4개"다
원안은 3층을 "공개하기로 한 사람들의 사본"으로 그렸다. 실제로는 **웹(`web/index.html`)이
지금 구독·작성하는 컬렉션이 정확히 4개뿐**이라는 사실이 결정적이었다(전수 grep 확인,
`guestbook`·`gallery`·`attendance`·`events` — `runs`·`comments`·`claps`·`profiles`는
웹 코드 어디에도 없음). 그래서:

| 컬렉션 | 층 | 이유 |
|---|---|---|
| `guestbook`·`gallery`·`attendance`·`events` | **root 그대로**(무이동) | 웹이 직접 씀 — 격리하면 웹·앱 실시간 동기화가 끊긴다 |
| `runs`·`comments`·`claps`·`profiles` | **`crews/{CREW_ID}/{col}`로 이동** | 앱 전용, 웹 영향 0. `runs`는 원래 "랭킹·통계 오염 방지"가 목적이던 컬렉션이라 크루 격리가 오히려 기존 결함(생판 남이 크루 랭킹 1등)을 고친다 |

이건 "옵트인 동의를 받은 공개 사본"이 아니라 **"웹 커뮤니티 쇼케이스가 원래 보던 것을 그대로
둔 것"**이다 — §4-1의 이동비용 논리(마이그레이션 0)와 결이 같지만 근거는 다르다.

### 11-3. `CREW_ID`는 여전히 정적 상수다 — 그래서 컷오버가 공짜였다
`crew.ts`의 `subscribe`/`add`/`remove`/`update`/`put`는 `col: string`을 그대로
`collection(db, col)`/`doc(db, col, id)`에 넘긴다. Firestore SDK는 이 문자열이 홀수
세그먼트(컬렉션)이기만 하면 `"crews/modu/runs"`처럼 다중 세그먼트도 그대로 받는다 — 그래서
`firebase.ts`의 `COLLECTIONS.{runs,comments,claps,profiles}` 정의 4줄만 바꾸면 소비 파일
9곳은 **코드가 한 글자도 안 바뀐다**(전수 grep으로 우회 0건 확인). `CREW_ID`가 사용자별로
달라지는(다중 크루 동시 소속·전환) 순간, 이 값은 세션 상태 기반 함수로 바뀌어야 하고 그때
9개 파일이 기계적으로 한 줄씩 바뀐다(tsc가 누락을 잡아준다).

### 11-4. 기존 사용자는 자동으로 크루 멤버가 된다
`crews/{CREW_ID}/{runs,comments,claps,profiles}`는 `isMember(crewId)`로 가려진다. 기존
사용자는 초대 코드를 입력한 적이 없어 멤버십 문서가 없다 — 그대로면 이번 업데이트로 전원이
자기 기록을 못 읽는 회귀가 생긴다. `crew.ts`의 `ensureCrewMembership()`이 로그인 직후 자동으로
`role: "member"` 멤버십을 만들어 이 회귀를 막는다(`_layout.tsx`에서 `ensureSignedIn()` 뒤에
호출). 두 번째 크루(PHASE 4)가 생기면 이 자동가입은 유일한 크루로의 이행 편의로만 남고, 새
크루 가입은 초대 코드 검증을 실제로 거치게 된다.

### 11-5. 데이터 마이그레이션
`app/scripts/migrate-crew-modu.mjs` — root의 `claps`·`profiles`·`runs`·`comments` 기존
문서를 `crews/modu/{col}/{id}`로 **복사**(§4-2 사본 원칙, root는 절대 안 건드림). idempotent.
`guestbook`·`gallery`·`attendance`·`events`는 이동 대상이 아니라 옮기지 않는다.

### 11-6. PHASE 3 이후에 적용할 원칙
"웹에 보이는 커뮤니티 쇼케이스"는 root, "앱 전용 운영·성과 데이터"는 crew-scope — 이 경계로
새 컬렉션도 판단한다. PHASE 3(코스·후기)·PHASE 4(목표·대회)는 웹에 없는 기능이므로 crew-scope.
다중 크루가 실제로 붙어 "웹이 크루를 선택해서 본다" UX가 생기면, 그때 guestbook 등 4개도
크루별로 쪼갤지 재검토한다.
