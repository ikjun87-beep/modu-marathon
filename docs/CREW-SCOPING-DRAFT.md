# 초안 — 크루 단위 데이터 격리 (BS 회의 입력자료)

> 이 문서는 **때릴 대상**이다. 적대적 회의(`/bs`)의 P1 입력으로 배포된다.
> 작성 2026-08-01. 회의 뒤 결론은 `docs/BRIEF.md`에 남는다.

---

## 1. 지금 상태 — 사실만

### 1-1. 데이터 격리가 **없다**
`firestore.rules`의 8개 컬렉션이 전부 `allow read: if true`(전체 공개)이고, 문서에
**크루를 구분하는 필드가 하나도 없다**(`crewId`·`groupId` 전무 — 코드 전수 검색으로 확인).

| 컬렉션 | 문서 모양 | 크루 구분 |
|---|---|---|
| `guestbook` | `{ name, msg, createdAt }` | ❌ |
| `gallery` | `{ name, caption, image(base64), createdAt }` | ❌ |
| `attendance` | `{ eventId, name, createdAt }` | ❌ |
| `runs` | `{ source, name, distanceKm, durationSec, startedAt, avgHr… }` | ❌ |
| `comments` | `{ parentId, name, msg, createdAt }` | ❌ |
| `events` | `{ title, desc, startAt, name, createdAt }` | ❌ |
| `claps` | `{ targetId, name, createdAt }` | ❌ |
| `profiles` | `{ name, photo(얼굴 base64), createdAt }` | ❌ |

### 1-2. 신원도 **이름 문자열**이다
- 앱: `session.ts`가 AsyncStorage에 러너 네임 저장. 문서에 `name`으로 **박제**된다.
- 개명하면 `crew.ts:renameAuthor()`가 과거 문서의 `name`을 일괄 수정한다.
  → 같은 이름을 쓰는 다른 사람의 문서도 함께 바뀐다(코드 주석에 한계로 명시돼 있음).
- Firebase Auth는 배선돼 있으나(익명·이메일) **소유권 판정에 쓰지 않는다.** `withUid()`가
  `uid`를 곁들여 저장할 뿐, 규칙은 uid를 보지 않는다.

### 1-3. 쿼리 방식
`crew.ts:subscribe()`가 **컬렉션 전체를 `orderBy(createdAt desc)`로 구독**한다.
필터가 없다. 화면은 받은 전체 배열을 클라이언트에서 가공한다.

### 1-4. 웹도 같은 컬렉션을 쓴다
`web/index.html`이 동일한 Firestore 프로젝트·컬렉션에 직접 접근한다(빌드 없는 정적 HTML).
앱만 고치면 웹이 깨지거나, 웹을 통해 격리가 뚫린다.

## 2. 무엇이 문제인가 — 구체적 손실

1. **모르는 사람에게 전부 보인다.** 플레이스토어에서 앱을 깐 누구든 내 이름·러닝 기록·
   크루 사진·방명록·**얼굴 프로필 사진**을 본다.
2. **처리방침과 실제가 다르다.** 2026-07-31 개정본은 프로필 사진을 "크루원 등 서비스
   이용자에게 공개"라고 적었는데, 실제 범위는 "앱을 깐 전원 + 링크를 아는 누구나"다.
3. **랭킹·통계가 무의미해진다.** 이번 주 1등이 생판 남일 수 있다.
4. **비공개 테스트 12명이 서로 다 보인다.** 지금은 그들이 실제 크루라 우연히 안 드러날 뿐이다.

## 3. 선택지 (초안이 미는 안 = A)

### A. 문서 필드 `crewId` + 규칙으로 격리 ★초안
모든 문서에 `crewId`를 넣고, 규칙에서 **내가 속한 크루의 문서만** 읽게 한다.
```
match /runs/{id} {
  allow read: if isMember(resource.data.crewId);
}
```
- 멤버십은 `members/{crewId}_{uid}` 문서로 판정(`exists()`).
- 쿼리는 `where("crewId","==",myCrew)` 추가.
- **Auth 필수**(uid 없이는 멤버십 판정 불가) → 익명 로그인 자동화.

**장점**: 컬렉션 구조 유지 → 화면·데이터 레이어 변경이 가장 적다. 한 사람이 여러 크루에
속하는 것도 나중에 열 수 있다.
**단점**: 모든 쿼리에 필터를 빠짐없이 넣어야 한다. **한 곳이라도 빠지면 규칙이 막아주지만
화면이 빈다**(조용한 버그). 복합 색인이 필요해진다(`crewId` + `createdAt`).

### B. 서브컬렉션 `crews/{crewId}/runs/{id}`
경로 자체로 격리한다.
```
match /crews/{crewId}/{col}/{id} {
  allow read: if isMember(crewId);
}
```
**장점**: 규칙이 짧고 명확하다. 경로에 crewId가 있으니 **필터를 빠뜨릴 수가 없다**.
**단점**: `COLLECTIONS` 상수·`crew.ts` 전 함수·웹 HTML의 경로가 전부 바뀐다. 재작업량 최대.
크루 간 통합 조회(전체 랭킹 같은 것)는 collectionGroup 쿼리가 필요하다.

### C. 크루마다 Firebase 프로젝트를 판다
**장점**: 물리적 격리. 규칙 변경 거의 없음.
**단점**: 크루가 늘 때마다 수동 작업. 앱에서 프로젝트를 바꿔 끼우는 구조가 필요.
**사실상 확산 불가** — 플레이스토어 앱 하나로 여러 크루를 받을 수 없다.

### D. 단일 크루 유지 + 크루별로 앱을 따로 배포
현 구조를 그대로 두고, 크루마다 패키지명을 바꿔 별도 앱으로 낸다.
**장점**: 코드 변경 0.
**단점**: 크루 하나당 스토어 등록·심사·12명 테스트를 반복해야 한다. 확산 포기.

## 4. 초안이 제안하는 가입 흐름 (A안 기준)

1. 첫 실행 → 러너 네임 입력(현행 유지) → **익명 로그인 자동 실행**(uid 확보)
2. 화면 두 갈래: **[크루 만들기]** / **[초대 코드로 참여]**
3. 크루 만들기 → `crews/{id}` 생성(이름·만든이) → **6자리 초대 코드** 발급
4. 참여 → 코드 입력 → `members/{crewId}_{uid}` 생성 → 그 순간부터 그 크루 데이터만 보임
5. 초대는 **링크 공유**(`5kilo://join?code=ABC123`)로도 — 카톡에 붙여넣기

## 5. 마이그레이션 (A안 기준)

지금 실데이터(회장 + 크루원 소수)를 **기본 크루 하나**로 묶는다.
- `crews/default` 생성 → 기존 전 문서에 `crewId: "default"` 일괄 주입(스크립트 1회)
- 기존 사용자는 앱 업데이트 시 자동으로 `default` 멤버로 편입
- ⚠️ 웹은 로그인 개념이 약하다 — 웹 방문자를 어느 크루로 볼 것인가가 미해결

## 6. 제약 (전 역할 공통 전제)

- Expo SDK 57 · Firestore(웹 SDK) · 웹(정적 HTML)과 **스키마 공유**
- **회장 혼자 개발·유지보수.** 복잡도가 곧 부채다
- 플레이스토어 **개인 계정 비공개 테스트 임박**(12명 · 14일 연속)
- 되돌리기 비쌈: 출시 후 구조를 바꾸면 남의 데이터까지 이관해야 한다
- 개인정보 노출 0은 **게이트**다(협상 대상 아님)
